# Faryo v1.12 App Server Session Isolation Plan

状态：实施中

架构依据见
[`../appserver-fault-isolation-audit.md`](../appserver-fault-isolation-audit.md)。本计划只记录公开、
匿名的状态与验收结果，不记录对话正文、真实 thread id、本机路径、域名、账户或认证材料。

## 目标

把 Faryo App Server 从“一个进程承载所有 Web 会话”迁移为“一个只读控制进程，加每个 Web
会话一个受监督 worker”。单个 Codex App Server 卡死、RPC 超时、进程退出或强制恢复时，只能
影响对应会话；不得再让其他 Faryo 会话、普通 Codex CLI 或 Codex TUI tmux 一起不可用。

## 架构边界

```text
faryo-appserver.service
  -> read-only control plane

faryo-appserver-worker@<opaque>.service
  -> one official codex app-server
  -> one Faryo Web thread

faryo-owner.service
  -> AppServerControlClient
  -> AppServerSessionSupervisor
       -> Session A client/actor/generation
       -> Session B client/actor/generation
```

- worker 标识是本机生成的不透明值，不使用标题、目录或 thread id；socket 只能位于 Faryo 私有
  runtime 目录。
- `faryo-appserver.service` 只负责账户、模型、只读 history/lifecycle 与 diagnostics，不恢复会话。
- 每个 worker 有独立 socket、systemd cgroup、重启计数、pending RPC、通知队列和 circuit breaker。
- Owner 继续负责浏览器 projection、可靠发送、命令 timeline、认证与 SSE；不把 systemd 或原始
  Codex 错误暴露给浏览器。

## 阶段

### Phase 0：冻结协议与故障注入基线

- [ ] 固定 Codex `rust-v0.149.1` schema/能力基线，并对更高版本使用生成 schema 与能力探测。
- [ ] 建立两个匿名 fake worker：A 可阻塞 RPC/忽略 TERM，B 持续流式响应。
- [ ] 记录当前 shared-process 的 writer、超时、close/unsubscribe 和服务重启行为。
- [ ] 给现有 AppServerRuntime 增加明确的 shared-topology 退役断言，防止新代码暗中回退。

### Phase 1：服务拓扑与持久注册表

- [ ] 新增 `faryo-appserver-worker@.service`，实例参数、socket 和停止目标均严格校验。
- [ ] 将 session registry 升级为 schema v2，增加不透明 worker id、代际和最近健康状态；v1 数据
  原子迁移且不改变浏览器 session 名称。
- [ ] 安装、升级、stop、restart、doctor、uninstall 识别并只管理 Faryo worker 实例。
- [ ] 共享 `faryo-appserver.service` 变为只读 control plane，加入“不得恢复 Web thread”的测试。

### Phase 2：每会话 Runtime

- [ ] 拆出 `AppServerControlPlane`、`AppServerSessionSupervisor` 和 `AppServerSessionRuntime`；禁止
  单例 client 处理多个 session actor。
- [ ] New/Resume 在写入注册表前启动并验证一个 worker；失败路径停止该 worker，不遗留 unit/socket。
- [ ] Owner 重启后按注册表连接原 worker；若 worker 已退出，则只重建该 worker 并恢复对应 thread。
- [ ] close 先处理 interaction/interrupt，再停止一个 worker，验证 writer 释放后删除注册表记录。
- [ ] account/rate limits、history archive/read 与 model catalog 走 control plane；turn、command、goal、
  approval 和 capture 只走对应 session worker。

### Phase 3：超时、恢复与 circuit breaker

- [ ] 每个 RPC 记录 worker、request id、generation、method class、dispatch 和 terminal state；超时清理
  pending，旧 generation 响应不能污染新进程。
- [ ] 普通 RPC、初始化、interrupt 和长 turn 使用不同 deadline；官方 `-32001` 只做有 jitter 的有界重试。
- [ ] 用 `server/diagnostics`/`thread/read` 建立低频有界 control probe；process-alive、raw cadence、
  responsive 和 user-visible progress 分开建模。
- [ ] 用户 Stop：先 `turn/interrupt`；短 grace 后仍未 settle，只回收该 worker，恢复 thread，并显示
  明确的 forced-recovery activity。
- [ ] 单 worker 连续失败进入 open circuit；健康 worker 不降级，浏览器得到稳定的 retryable 错误码。
- [ ] ambiguous send 只用原 `clientMessageId` 对账，不生成第二条用户消息。

### Phase 4：安全迁移与产品状态

- [ ] 升级前检查活动 turn/interaction；不安全时明确延期，不在运行中强迁共享进程。
- [ ] 安全迁移顺序：停 Owner → 重启只读 control 以释放 shared writers → 启动 per-session workers →
  启动 Owner/Gateway → 对账 registry、writer 与历史。
- [ ] Details 展示 `Codex App Server` 与该会话的 Ready/Reconnecting/Degraded 状态，不显示 PID/socket。
- [ ] diagnostics 只提供计数、状态、错误类别、代际和时间，不记录正文、路径或 thread id。
- [ ] 普通 reload 自动获得新资产；旧资产请求与拒绝响应保持 `no-store`。

### Phase 5：验收、部署与发布

- [ ] A 的 RPC 永久阻塞时，B 的流式增量、发送、interrupt 和 capture 在既定延迟内继续成功。
- [ ] 强制恢复 A 后，B 的 PID/代际/turn 均不变；A 能恢复同一 thread 并接受下一轮。
- [ ] 一个 App Server thread 被 Faryo 持有时，另一个普通 Codex CLI 新会话仍可立即使用；同一 thread
  冲突则快速返回清晰错误，不等待或卡死全局 CLI。
- [ ] worker 忽略 TERM 时只升级为该 unit 的 KILL，并验证无孤儿进程和 writer lock。
- [ ] Owner/Gateway 普通重启、网络断开、worker crash、超时 late response 和重复发送均有自动测试。
- [ ] source、浏览器、真实 Codex、部署、普通 reload、tmux 几何、Markdown/TeX、历史和认证门通过。
- [ ] 合并功能分支、推送 main，发布 source-only v1.12.0，并提供从 v1.11.x 的安全回滚说明。

## 完成定义

只有当故障注入证明“一个 worker 卡死不会拖累另一个 worker 或普通 CLI”，且真实部署中的
服务、writer、发送、历史、公式与 tmux 门均通过，才能把本计划标记为完成。仅增加 timeout、
重启整个共享服务或改善报错文案不算完成。
