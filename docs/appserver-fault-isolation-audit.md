# Codex App Server Fault-Isolation Audit

Date: 2026-08-25

This audit compares Faryo's current Codex App Server ownership model with the
official Codex runtime and three actively maintained self-hosted clients. It is
limited to public architecture, lifecycle and test evidence. No private
conversation content, host path, account, domain, credential or runtime
identifier is included.

## Executive conclusion

Faryo 1.11.11 has a sound protocol client but the wrong failure boundary for
independent conversations: one long-lived `codex app-server` process resumes
every active Faryo App Server thread. That saves processes, but combines all
Web sessions into one process, transport and writer-lock failure domain.

The selected v1.12 design is:

```text
read-only control App Server
  - account, model, history and lifecycle reads
  - never resumes a Faryo conversation

one supervised App Server worker per Faryo Web session
  - one private Unix socket
  - one official Codex App Server process
  - one thread writer domain
  - one reconnect/circuit-breaker state

Owner
  - routes each session only to its worker
  - keeps browser projection and reliable-send semantics
  - can restart one failed worker without touching another session or tmux
```

The guarantee is deliberately precise: a failed or wedged Faryo App Server
worker must not block an unrelated Web session, ordinary Codex CLI thread, or
Codex TUI tmux session. Faryo cannot promise that an upstream Codex process,
model request or tool can never hang.

## What the official App Server requires

The official runtime already provides several mechanisms Faryo should use
rather than infer:

- requests, processing and outbound writes use bounded queues; overload is a
  retryable JSON-RPC `-32001` response;
- one process may load several threads, but only one App Server process may
  hold a paginated thread open for writing;
- `thread/unsubscribe` removes a connection subscription but deliberately
  keeps the thread loaded for up to 30 minutes before idle unload;
- `thread/loaded/list`, `thread/read`, `thread/status/changed` and
  `server/diagnostics` expose explicit state and health evidence;
- `turn/interrupt` is the supported cooperative stop mechanism; process
  termination is a client-side last resort;
- protocol schemas are generated by the installed Codex version and may
  evolve, so compatibility must be checked against the exact supported tag.

The 30-minute unload rule explains why unsubscribe alone cannot provide fast
writer release. Restarting a shared process releases the writer immediately,
but also interrupts every other thread loaded in that process.

## Current Faryo failure path

The current topology is:

```text
faryo-appserver.service
  -> one codex app-server --listen unix://...
       -> thread A writer
       -> thread B writer
       -> thread C writer

faryo-owner.service
  -> one AsyncCodexAppServerClient
  -> one AppServerRuntime event loop
  -> actors A, B and C
```

The client itself has useful protections: bounded RPC waits, a pending-request
map, a bounded notification queue, reconnect backoff, one reader, serialized
writes and idempotent browser delivery receipts. The structural problems are
above that layer:

1. `_restore_sessions()` resumes every registered Web thread through the same
   process, so one process holds all corresponding writer locks.
2. A transport disconnect or protocol queue failure reconnects the one shared
   client and rehydrates every actor.
3. A timed-out RPC removes its pending future, but the shared upstream process
   remains the only execution path for all sessions.
4. Closing a session sends `thread/unsubscribe`; the writer may remain for 30
   minutes. Faryo can recycle the process immediately only when the final Web
   session closes, because recycling it earlier would interrupt the others.
5. A health check can say the shared socket is alive while one or more loaded
   thread runtimes are unhealthy. Process-alive is weaker than per-thread
   progress or a successful bounded control probe.

This is why incremental timeout text alone cannot solve the severe freeze
class. The ownership topology must change.

## Lessons adopted from the reference clients

### HAPI

- The session launcher owns one App Server client and child process.
- Request dispatch and request completion are distinct states. If a write may
  have reached Codex, the outcome is indeterminate and must not be blindly
  replayed.
- Pending requests are removed on response, timeout, abort, process exit and
  disconnect. A protocol generation prevents an old process response from
  satisfying a new request.
- Transport abandonment wakes the session loop, which can recover on a fresh
  App Server without corrupting another session.

### Happy

- Each session has a process epoch; late exit and response events from an old
  process are ignored.
- Ordinary RPCs are bounded. Turn completion has a separate, longer deadline.
- Stop first sends `turn/interrupt`. If the turn does not settle within a short
  grace, Happy restarts only that session's App Server and resumes its thread.
- A stale interrupt must settle before a later `turn/start`, otherwise it can
  abort the wrong turn.

### YepAnywhere

- One provider child and process group belong to one session. Cooperative
  TERM escalates to KILL and shutdown is positively verified.
- Process exit is a distinct terminal runtime error, not a failed assistant
  turn and not silent waiting.
- Raw provider cadence, process-alive and user-visible progress are separate
  evidence. A bounded active probe can verify responsiveness without claiming
  visible progress.
- Its durable host design correctly notes that preserving only a PID is not
  enough for hot reload: the complete protocol owner includes request maps,
  approvals, event replay and current-turn state.

## Selected scope and non-goals

v1.12 will implement per-session official App Server workers supervised by
systemd user template units. This fits Faryo's existing deployment model and
avoids inventing a second general-purpose daemon.

The first release will preserve history and reconnect after Owner restart, but
will not claim lossless continuation of an approval that is created during the
brief interval in which Owner is offline. Deployment and restart commands must
therefore defer while an App Server turn or interaction is active. A future
durable protocol-owner process is justified only if lossless active-turn hot
reload becomes a product requirement.

The change will not:

- adopt a framework rewrite or replace Python/Starlette;
- modify Codex TUI geometry or take ownership of desktop tmux sessions;
- copy HAPI's AGPL implementation;
- retry an ambiguously accepted user message with a new delivery identity;
- kill arbitrary `codex`, `node`, tmux or shell processes by name;
- expose prompts, paths, thread ids, credentials or raw stderr in public
  diagnostics.

## Required invariants

1. Worker A timeout, crash, restart or forced stop leaves worker B's PID,
   transport generation, turn and writer lock unchanged.
2. A worker owns at most one root Faryo Web thread; a thread has at most one
   Faryo worker.
3. The control App Server never calls `thread/start`, `thread/resume` or
   `thread/fork` for a Faryo Web session.
4. Every RPC has a request id, generation, bounded deadline and exactly one
   terminal ledger transition.
5. Delivery distinguishes not-dispatched, accepted, rejected and indeterminate
   outcomes. Only the same message id may reconcile an indeterminate send.
6. Stop is cooperative interrupt first, bounded per-worker recycle second.
7. Worker teardown targets only its validated systemd instance and private
   socket; cleanup verifies process and writer release.
8. Browser refresh, Gateway reconnect and history reads never interrupt a
   worker.
9. TUI sessions, external Codex clients, Markdown/TeX, authentication and
   tmux geometry retain their existing contracts.
