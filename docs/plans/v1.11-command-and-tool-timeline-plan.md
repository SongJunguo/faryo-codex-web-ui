# Faryo v1.11 Command and Tool Timeline Plan

状态：实施中

基线：Faryo `1.10.3`，`main` 提交 `1394f72`

开始日期：2026-08-23

## 1. 问题与结论

Faryo 已能从 Codex App Server 持续接收正文、计划和工具事件，但当前展示链路仍把
`commandExecution`、`fileChange`、search 和 MCP 调用提前压成一句纯文本，浏览器再用正则
猜测它们的类型。这个有损转换造成三个直接问题：

1. `/rename`、`/model`、`/fast`、`/permissions` 等由网页执行的会话命令不属于模型
   transcript，完成后没有可恢复的时间线记录；刷新后用户只能看到结果变化，看不到发生过
   什么操作。
2. 命令输出、文件变更状态、工具错误和耗时在纯文本投影中丢失；短项目看起来像“完全没
   显示”，长项目则混成不可辨认的代码块。
3. 当前折叠规则依赖英文前缀和字符长度，Codex 增加事件类型或改变文案后容易误分类。

本阶段不把本地命令伪装成用户消息，也不把它们提交给模型。Faryo 将建立三条明确分离的
展示通道：

- 用户与 Codex 正文：继续以 Codex thread/rollout 为唯一真相来源；
- Codex 工具活动：保留官方 item 类型、稳定身份、生命周期和按需详情；
- 用户会话命令：使用独立、受限、可恢复的 command lifecycle，记录展示所需事实而不记录
  敏感正文。

## 2. 参考设计与许可证边界

- DeepSeek Harness：借鉴 command run/done 的独立生命周期、稳定 command id 和不进入模型
  turn 的事件边界；命令参数按类型决定是否可记录。
- Yep Anywhere：借鉴轻量 system row、默认折叠详情、稳定消息身份和刷新后恢复语义。
- HAPI：只研究 typed tool begin/end、工具分组和详情层级。HAPI 为 AGPL-3.0-only，本项目不
  复制其实现代码、样式或测试 fixture。
- Codex App Server：以 `item/started`、`item/completed`、output delta、
  `thread/name/updated` 和 `thread/settings/updated` 为协议事实，不解析终端像素来模拟
  App Server 会话。

参考项目只用于 clean-room 行为研究；公开归属和固定参考提交继续记录在现有 reference
audit 中。

## 3. 用户可感知结果

- 执行 `/rename` 后，标题立即更新，并在对话中出现类似“Renamed conversation”的紧凑系统
  行；普通刷新、断线重连后仍存在。
- `/model`、`/fast`、`/permissions`、`/goal` 的成功、失败或等待选择状态可辨认；读取型面板
  不制造无意义的 transcript 噪声。
- 每轮工具活动先显示一行摘要，例如命令、文件修改、搜索和其他工具数量。默认折叠；正在
  运行、失败和等待批准的项目优先可见。
- 展开后每个项目有类型、状态和简短标题；命令输出、文件 changes/diff、MCP 结果按需展开，
  长输出有明确截断提示，不再把整段原始协议对象直接塞进对话。
- 未识别的新 Codex item 使用安全的通用卡片，不因版本变化消失或破坏整轮渲染。
- 复制回答仍只复制原始 Markdown/TeX 正文；系统命令和活动卡片不混入回答复制结果。

## 4. 数据与隐私边界

1. 不建立第二份 prompt/answer 数据库；正文继续来自 Codex。
2. command timeline 只保留显示所需的白名单字段、稳定随机 id、状态和时间。文件模式为
   `0600`，父目录为 `0700`，写入采用原子替换与 fsync。
3. `/goal` objective、任意用户消息、Token、Cookie、邮箱、域名和认证头不得进入 command
   timeline、诊断、日志或公开 fixture。
4. `/rename` 标题属于已有私有会话元数据，可以在本机私有 timeline 中显示；公开测试只使用
   匿名标题。
5. 模型、speed 和 permissions 只记录经过白名单归一化的选择值；未知或自由文本参数默认只
   记录命令名，不记录参数。
6. 工具详情按类型设置独立字节上限；超限时保留头尾和 `truncated` 标记。浏览器不接收原始
   App Server id、本机绝对目录之外的协议对象或隐藏 reasoning。
7. body-free SSE journal、security audit 和 diagnostics 保持 body-free；私有展示 timeline 不得
   被这些接口枚举或导出。

## 5. 领域模型

### 5.1 Session command

一个命令事件至少包含：

- `id`：服务端生成的稳定不透明身份；
- `session` / `thread`：仅用于本机归属，向浏览器投影时隐藏 raw thread id；
- `name`：规范命令名；
- `label` / `summary`：服务端从类型和结果生成的惰性文本；
- `status`：`running`、`waiting`、`completed` 或 `failed`；
- `anchorTurn`：命令发生时最近的 Codex turn，用于时间线定位但不创建伪问题；
- `startedAt` / `completedAt` 和可选安全 metadata。

同一个 `clientRequestId` 重试必须返回同一 command id 和结果，不生成重复行。交互式
`/model`、`/permissions` 等从 `waiting` 到 `completed` 复用同一事件。

### 5.2 Tool activity

浏览器 block 在已有 `id`、`turnKey`、`kind`、`text` 上增加受限的 `activity` 对象：

- `type`：`command`、`file_change`、`search`、`mcp`、`tool`、`image`、`compaction`、
  `error` 或 `unknown`；
- `status`：`running`、`waiting`、`completed`、`failed` 或 `declined`；
- `title` / `summary`：短文本；
- `detailAvailable`、`detailKind` 和受限统计字段；
- 可选的安全 inline preview，不携带完整详情。

详情通过认证、`no-store` 的单项接口按需获取。详情不可用时明确显示原因，不用空白卡片
假装成功。

## 7. 验收标准

1. `/rename Anonymous title` 成功后标题和 system row 都在 1 秒内更新；Owner 重启、普通 reload
   后仍只出现一次，且不进入发送给 Codex 模型的用户消息。
2. `/model` 打开选择器时对应事件为 waiting；选择后原位完成。取消也原位结束，不产生伪回答。
3. 一轮包含 command execution、file change、search、MCP 和失败项时，折叠摘要计数准确；展开
   能看到对应类型的受限详情，失败无需展开即可识别。
4. 未知 App Server item 不导致整轮丢失；至少显示通用活动标题、状态和“details unavailable”。
5. 200 个 turn、1,000 个 activity item 的匿名 fixture 中，初始 DOM 不展开详情正文；历史前插
   锚点、滚动和正文流仍通过既有性能门。
6. command store 损坏、超限、symlink 和跨 session item 查询全部 fail closed；公开仓库扫描无
   私密数据。
7. 普通 reload 获取所有新 JS/CSS module 的同一 release revision；缺失或拒绝资产为 no-store。
8. 可靠发送、Markdown/TeX、Raw/Chat、copy、Goal、历史分页、移动键盘、认证、Cloudflare
   路由和 tmux geometry 的既有回归测试全部通过。
